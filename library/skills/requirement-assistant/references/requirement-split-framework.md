# 需求拆分框架

## 定位

需求拆分是将复杂需求切分为可独立交付的子需求（子 Story）的过程。

**核心理念**：
- **拆分策略是"刀"**——决定从哪里切（怎么拆）
- **INVEST 是"尺子"**——检验切出来的每块是否合格（拆得好不好）
- **AI 识别信号，人做决策**——AI 从需求内容中提取信号并给出建议，人做最终判断

## 一、是否需要拆分

先判断，不是所有需求都要拆：

| 信号 | 判断 |
|------|------|
| 单一功能、单一数据流、改动集中在同一模块 | **不拆** |
| 包含 ≥2 个可独立验证的子功能 | **拆** |
| 需求本身已足够简单 | **不拆** |

## 二、拆分维度

### 主切维度（三选一，决定第一刀怎么切）

| 维度 | 选择条件 | 切法 |
|------|---------|------|
| **业务流程** | 需求描述了多步骤流程（如注册→审核→开通→计费） | 按流程节点切 |
| **功能模块** | 需求列举了多个独立功能点（如新增A、优化B、修复C） | 按功能点切 |
| **架构/技术栈** | 需求涉及多个服务或多种技术栈（如前端+后端+SDK） | 按服务或技术栈切 |

**选择逻辑**：
```
需求里有多步骤流程描述？ → 业务流程优先
需求里有多个独立功能点？  → 功能模块优先
需求里涉及多个服务/技术栈？ → 架构/技术栈优先
```

### 辅助维度（按需叠加，调整拆分结果）

| 维度 | AI 识别的信号 | AI 的建议 | 人的决策 |
|------|-------------|----------|---------|
| **风险等级** | 数据安全相关、线上影响、大范围变更、核心链路 | 高风险项单独拆出 | 确认风险判断是否合理 |
| **交付优先级** | 需求类型（Bug修复>新功能>优化）、显式标注（"紧急"/"P0"/"先上线"）、依赖关系、客户绑定 | 被依赖的先做、有客户的优先、依赖未就绪的后置 | 确认优先级排序是否符合业务实际 |
| **工作量规模** | 接口数量、涉及模块数、新增vs修改、是否有数据迁移、是否有外部依赖 | 复杂度标注：低/中/高；高复杂度建议继续拆，多个低复杂度建议合并 | 确认粒度是否合适 |

**AI 不估绝对工时、不定义绝对优先级——只识别信号并给出建议，人做最终决策。**

### 领域维度（仅特定场景触发）

| 维度 | 触发场景 |
|------|---------|
| **数据流** | 数据平台/日志系统，数据从采集到消费的管道 |
| **合规域** | 涉及等保/GDPR/内审等不同合规要求 |
| **模型生命周期** | AI/算法需求，训练→评估→推理→监控 |

## 三、质量门禁：INVEST 检验

拆分完成后，对每个候选子需求逐条检验：

| 检验项 | 问题 | 不通过时的处理 |
|--------|------|---------------|
| **Independent** | 这个子需求能独立上线吗？ | 有强依赖则合并，或明确依赖方向 |
| **Valuable** | 单独交付有用户价值吗？ | 无独立价值则合并到关联子需求 |
| **Testable** | 有明确验收标准吗？ | 无法验证则补充验收条件或重新拆 |
| **Small** | 单次迭代能完成吗？ | 太大则继续拆 |
| **Negotiable** | 实现方式有灵活空间吗？ | 过于刚性则重新评估 |
| **Estimable** | 能估算工作量吗？ | 估不出则补充细节 |

**任何一条不通过 → 回溯调整拆法或合并，重新检验。**

## 四、拆分产出

| 项目 | 说明 |
|------|------|
| **产出类型** | 子需求（子 Story），不是 Task |
| **创建方式** | 通过 TAPD API 创建子需求并关联到父需求 |
| **为什么是子需求** | INVEST 要求每个拆分结果独立有价值、可测试、可上线，这是子需求的定义，Task 做不到 |
| **子需求特性** | 可独立设置负责人、优先级、状态；可建立依赖关系；可分批上线和验收 |

## 五、完整流程

```
获取需求 → 是否需要拆分？
              ├─ 否 → 不拆，输出结论
              └─ 是 → 选主切维度（三选一）
                       → 辅助维度调整（风险/优先级/工作量，按需叠加）
                       → 领域维度（如触发）
                       → INVEST质量门禁检验
                          ├─ 通过 → 生成拆分报告
                          └─ 不通过 → 回溯调整拆法
                       → 用户确认
                          ├─ 确认 → 创建子需求并关联父需求
                          └─ 修改 → 调整后重新确认
```

## 子需求 TAPD Description 写入模板

创建子需求时，`description` 字段按以下格式写入（非拆分报告，是写入 TAPD 的实际内容）：

```markdown
## 需求描述（必选）
[详细功能说明，包含做什么和边界]

## 验收标准（必选）
- [ ] [仅写有依据的验收条件，不编造性能/安全/兼容性指标]

## 技术方案（可选，有实现复杂度时才写）
[实现思路，不涉及具体文件/类名。简单改动无需此章节]

## 依赖（可选，有依赖时才写）
[依赖子需求XXX]
```

**与拆分报告的区别**：拆分报告面向用户审阅，包含概览、INVEST 检验等；此模板面向 TAPD，聚焦需求描述+验收+技术方案+依赖，是子需求被创建后的实际内容。

**章节按需输出规则**：
- **必选章节**必须填写，不可省略
- **可选章节**仅在内容有实质意义时输出，不输出空壳或废话填充
- 严格按照模板结构输出，不扩展、不增加额外章节
- 验收标准仅写有父需求原文依据的条件，不得推断父需求未提及的指标

**设计原则**：
- 用"需求描述"而非"范围/功能点"——叙述体比条目式更适合描述子需求的完整功能，边界信息自然融入描述中
- 验收标准用 checkbox——TAPD 中可直接勾选跟踪进度
- 技术方案为可选——文案修改、配置变更等简单改动无需编造技术方案
- 依赖为可选——独立子需求无需编造伪依赖

## 不拆分时的输出模板

```markdown
# 需求拆分判断

- **总需求**：[需求标题]
- **需求ID**：[story_id]
- **是否需要拆分**：否
- **判断依据**：[如"需求为单一功能、改动集中在同一模块，不具备独立可交付的子功能"]
```

## 注意事项

1. 保持拆分逻辑透明，解释关键决策（为什么选这个主切维度、为什么触发这个辅助维度）
2. 粒度控制：基于复杂度信号判断，不设硬性数量上限；避免功能割裂，也要避免子需求过大无法单次迭代完成
3. 所有子需求创建必须经用户确认后执行，禁止自动创建
4. AI 不估算绝对工时、不定义绝对优先级——只识别信号并给出建议，人做最终决策
5. 需求信息不完整或存在歧义时，暂停拆分并向用户确认，不基于模糊信息推断拆分
