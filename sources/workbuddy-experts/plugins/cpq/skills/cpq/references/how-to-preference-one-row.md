# 针对老商品库（spu_id）产品进行精细配置优惠。

## 前提条件

- 已通过折扣计算或其他方式获得了部分产品的优惠数据
- 如果没有一个产品拥有优惠数据，就**跳过本步骤**

## 先过滤分流：批量处理无条件行，逐行精配带条件行

设置优惠前，先把全单**有优惠数据的产品**按优惠信息形态过滤分流成两组，分别处理：

| 优惠信息形态                                                                                      | 归组                     | 处理步骤                  |
| ------------------------------------------------------------------------------------------------- | ------------------------ | ------------------------- |
| **仅含折扣值**（如 `8折`,`80%`,`0.8`），**或仅含一口价**（如 `5元`,`5元/月`），且不带任何附加条件 | **A 组 · 无条件单一值**  | **第一步 · 批量写入**     |
| **含折扣值 / 一口价以外的任何条件**（地域、多档策略等），**或同一行含多个不同优惠值**             | **B 组 · 带条件 / 多值** | **第二步 · 逐行精细配置** |

本流程是**一条有序流水线**：先把 A 组所有行用一次批量写入（第一步），再逐个对 B 组行做逐行精配（第二步）。若 A 组为空则直接从第二步开始，B 组为空则只跑第一步。

> 🚫 **铁律 · 分流即安全闸**：优惠描述出现任何限定维度（地域、可用区、时长、规格、档位…）即为条件型，一律入 B 组；即使所有条件下优惠值相同，也不能分入 A 组。把带条件 / 多值行误判进 A 组批量，等于绕过第二步的逐行精细配置，是本流程最危险的错误。

## 取值铁律（A / B 组通用）

分流铁律决定「行进哪组」，取值铁律决定「值怎么写」。

> 🚫 **铁律 · 不支持优惠的产品必须跳过**：优惠信息为「产品不支持优惠申请」时，**不设置 `preference` 字段**，直接跳过该行。强行设置会导致 CPQ 报错「未获取到有效的优惠策略」。注意：「10 折」**不是**"不支持优惠"，而是设置 `{"preferenceType":"discount","value":1}`（= 原价 = 不打折）。

> 🚫 **铁律 · 折扣值精度不可损失 + 必须消除浮点尾差**：折扣统一按「折数 ÷ 10」表达：6.5 折 → `0.65`、3.919 折 → `0.3919`、2.61 折 → `0.261`。**转换必须用 `round(float(折数) / 10, 8)`**——`round` 不可省略（不 round 会产生 `0.26099999999999998` 这样的浮点尾差，CPQ 会拒绝）。。

> 🚫 **铁律 · 折扣值和一口价的小数长度不能超过 8 位**：CPQ 系统有硬限制——**小数部分最多 8 位**（submit 时校验）。但**≤8 位就必须原样保留，禁止主动 round 到更少位**——例如一口价单价 `0.00126666`（8 位，合法）不要再 round 成 `0.0012667`（7 位），否则折后金额会差几十元（已复现：15650_postpay 因此含税差 ￥21）。

> 🚫 **铁律 · 带条件优惠必须用 policyList**：
> - 源数据含"地域"、"可用区"、"服务区域"、"规格"等条件词，或含"策略1"、"策略2"等多策略时，**必须**用 `preference` 字段 + `policyList`（完整格式），**禁止**用简写的 `{"preferenceType":"discount","value":0.85}`（简写会丢失条件，变成全量生效）
> - **禁止**只提取第一条策略的折扣值——必须解析每一条策略的条件和值，构建完整的 `policyList` 数组

> 🚫 **铁律 · 禁止合并策略**：即使多条策略的折扣值相同，也**必须逐条写入 policyList**，一条策略对应一条 policy。
> - ❌ 禁止：源数据 68 条策略（每条 1 地域、同折扣），合并为 1 条 policy + 68 个地域数组
> - ✅ 正确：源数据 68 条策略 → policyList 有 68 条 policy，每条 `{"conditions":{"1":"gz"},"value":0.6}`
> - 理由：CPQ 系统按 policy 粒度展示和管理优惠，合并后无法还原原始的逐地域策略结构

> 🚫 **铁律 · 二次修补优惠时禁止凭记忆重写 conditions**：某行优惠**已设置成功后**再回头修（如修一口价精度、改折扣值），**只允许改要修的那个字段（通常是 `value`），必须原样保留该行已有的 `conditions`**。
> - ❌ 禁止：为改 `value` 精度而重写整个 preference，`conditions` 里的 attr_id / code 凭印象或照抄别的行填（例：另一款一口价产品的地域 id 是 `95`，就把本行也写成 `{"95":"bj"}`，而本行实际是 `{"2":"bj"}` → CPQ 报"非法的属性ID"）
> - ✅ 正确：先 `row cat --key preference --id <本行id>`（或 `row list --fields preference` 读回本行现值）拿到本行真实的 attr_id 与 code，只替换 `value`，`conditions` 不动
> - 理由：attr_id 和 code 是**每个产品各自定义**的，同类型（如都是 fixed_price）不代表 id 相同；跨行套用必然错。

## 分流门控（不可跳过）

> 🚫 **铁律 · 分流结果必须先展示再执行**：在执行第一步和第二步之前，必须先完成分流并输出分流清单：
> - A 组（无条件单一值）: N 个产品
> - B 组（带条件/多值）: M 个产品
> - 跳过（不支持优惠）: K 个产品
>
> **B 组数量 > 0 时，禁止把 B 组行的优惠用 preference 简写处理**——这是最常见的"偷懒"错误，简写会导致系统自动展开全部地域（把"贵阳 6.5折"变成"全部 37 个地域 6.5折"）。B 组必须走第二步的 policyList 完整格式。
>
> **关键判定规则**：即使源数据只有**一条策略、一个折扣值**，只要优惠文本中出现了"地域"/"可用区"/"服务区域"/"规格"/"策略"任一词，就**必须入 B 组**使用 policyList。
> - ❌ 错误：源数据"策略1 地域：贵阳，6.5折" → 用简写 `{"preferenceType":"discount","value":0.65}` → 结果：全部地域都被设为 6.5折
> - ✅ 正确：源数据"策略1 地域：贵阳，6.5折" → 用 policyList `{"preferenceType":"discount","policyList":[{"conditions":{"attr_id":"gy"},"value":0.65}]}` → 仅贵阳 6.5折
>
> **判定关键词**：优惠文本中出现以下**任一词**即为 B 组：`策略`、`地域`、`可用区`、`服务区域`、`规格`、`指定价`、`一口价`。即使所有条件下优惠值相同，也必须入 B 组。
>
> **特别注意一口价**：所有含"一口价"的行都是 B 组（因为一口价总是带地域条件的）。
> - `preferenceType` 必须用 `"fixed_price"`（**下划线格式**），❌ 禁止用 `"fixedPrice"`（驼峰，系统不认识会静默丢弃）
> - `value` 必须是一口价的**单价值**（如 `0.00456`），不是折后总价
> - 必须用 policyList + conditions 格式，不能用简写

## 第一步 · 批量写入无条件单一值行（A 组）

> 仅处理分流中判为 A 组（无条件单一值）的产品；若 A 组为空则跳过本步。

1. 将 A 组所有产品的优惠数据组装为单个 JSON 对象（以产品节点 ID 为 key）
2. A 组使用 `preference` 字段的简写格式：
   - 折扣：`{"preference": {"preferenceType": "discount", "value": 0.85}}`
   - 一口价：`{"preference": {"preferenceType": "fixed_price", "value": 500}}`
3. 使用 `--compress` 压缩传输（`compressed = base64(zlib.compress(json))`）
4. 执行：`row batch-update --compress {compressed} --cpqcode {code}`
5. CLI 会校验并批量执行；若某些行校验失败，根据错误信息修复对应字段后重新执行

## 第二步 · 批量/逐行精细配置（B 组）

> B 组 = 带地域/规格条件的优惠，或含多条策略的行。**必须用 `preference` 字段。**

> ⚠️ **元信息一律现场探索**：该行支持的优惠类型、条件字段 id、可选 code、value 格式，都以该行 `row cat` 的实际返回为准，禁止依赖记忆、文档或其他行。**不存在"地域 attr_id 固定是 1 或 2"这种事**——同一维度在不同产品 attr_id 可能是 `1` / `2` / `95` / `210` / `290` / `369` / `752` … 任何值，只能从该行 `row cat` 读，猜一个必然踩「非法的属性ID」。

### B 组处理原则（先读这一段再动手）

> **可以用脚本"组装 + 提交"，但严禁用脚本"解析"。** 三条硬边界：
>
> 1. ✅ **解析靠人 + row cat**：每行的条件维度、attr_id、取值 code，必须来自**逐行 `row cat`**（结构化元数据）+ 你**人工**把该行优惠文本拆成一张"拆解表"（见 Step 1）。
> 2. ❌ **禁止脚本正则解析自由文本**：绝不允许写脚本对 Excel 的 `优惠信息` 自由文本列跑正则（`re.findall` / `re.search` / `split`）批量抽取地域 / 折扣 / 维度。
> 3. ❌ **禁止硬编码 / 全局 attr_id·code 字典**：`SPECIAL_ATTR_IDS`、`REGION_MAP` 这类跨行复用的字典一律禁止；attr_id 和 code 只能来自**该行自己**的 `row cat`。
>
> 脚本只能做两件事：① 把你已核对的**拆解表**（结构化 JSON）机械拼成 policyList；② `--compress` 批量提交。**"从优惠文本得到拆解表"这一步没有捷径，必须逐行人工过 `row cat`。**

> ⚠️ **为什么"正则解析自由文本 / 全局字典"必须禁**——已复现的真实翻车（同一份 177 行清单，优惠维度一度 0/20、57 行错，并伴随硬报错）：
> - `re.search(r'地域[：:]\s*([^，,]+(?:[、，,][^，,]+)*)', text)` 把**折扣 token 吞进地域串**：`"地域：广州、上海，4 折"` → `["广州","上海","4 折"]`，`"4 折"` 被当 code（compare 报 `策略多出 [地域=...,4 折]`）。
> - 只解析地域、**漏掉其它维度**（`指定价=1` 被丢 → `策略缺失 [地域=gy, 指定价=1]`）。
> - 策略切分把**多条塌成一条**（`策略数: 68 → 1`）。
> - `else: append(原文)` 把中文名 / 未知词直接当 code。
> - 硬编码 `SPECIAL_ATTR_IDS` 猜 attr_id → CPQ 直接拒：`条件中包含非法的属性ID: 210/290`。
>
> 这些坑的共同点：**输入是自由文本 + 跨行套用的字典**。改用"逐行 `row cat` + 人工拆解表 + 脚本仅组装/提交"后，这些坑从源头消失。

按以下 6 步闭环执行，**每一步都不可跳过**（Step 0–2 逐行人工，Step 3–4 脚本可代劳，Step 5 强制回查）：

### Step 0 · 读取该行的优惠配置元数据

`row cat --key preference --id <row_id>` — 返回：支持的**优惠类型**列表、每个类型下的**条件字段**（字段 id、是否必填、单选/多选）、每个条件字段的**可选值 code 列表**。

### Step 1 · 人工把该行优惠文本拆成"拆解表"

对着该行的原始优惠文本 + Step 0 的 `row cat`，**人工**拆出一张结构化表：每条策略一行，列出「该策略涉及的每个维度 → 取值（先写中文/原文，Step 2 再换 code）」和「优惠值」。有几个不同优惠值就有几条策略。

**拆解表示例**（源"策略1 地域：贵阳，指定价：1GE，6.5 折"）：

```json
[
  {"维度": {"地域": ["贵阳"], "指定价": ["1GE"]}, "优惠值": 0.65}
]
```

- 表里的**维度个数**就是最终 `conditions` 的 key 个数——源文本里并列出现几个维度名（地域/指定价/可用区/服务区域/规格/带宽结算方式…），表里就必须有几个维度，**一个都不能漏**。
- 表里的**策略条数**就是最终 `policyList` 的条数——源有 68 条就 68 条，**不许塌缩**。
- **只有这张人工核对过的拆解表，才允许交给脚本去拼 JSON（Step 3）**；脚本**绝不能**跳过这张表、直接去 regex 原始优惠文本。

> 🚫 **差异禁抹平**：同一维度下不同取值对应不同优惠值时，禁止用多数取值的优惠值覆盖少数取值。

### Step 2 · 把条件值映射为合法 code（不得用原始文本）

- 条件值（中文名 / 顿号串）必须逐个在 `row cat` 返回的可选值表里查到 code 后写入。
- 同名条件在不同产品的 attr_id 可能不同，必须各自 `row cat`，禁止跨行复用。
- 🚫 **禁止建全局映射字典**：不得把多个产品 `row cat` 返回的地域 / 服务区域取值表**合并成一个全局 `name→code` 字典**再套用到所有行——同一个中文名（如「天津」「南美区」）在不同产品可能对应不同 code，全局合并会「后写覆盖先写」导致张冠李戴。每行的 code 只从**该行自己的** `row cat` 结果里查。
- **非地域条件也必须映射**：如「远端及目的端地域：中国大陆到中国大陆」→ 查 `row cat` 可选值表得 `mainland_to_mainland`，写入 `{"752": "mainland_to_mainland"}`。
- ❌ 禁止：条件值为空（`"conditions": {}`）或条件值留中文名（`"conditions": {"752": "中国大陆到中国大陆"}`）→ CPQ 会忽略条件，导致优惠条件丢失。
- 🚫 **铁律 · 条件值只写 inbox 中明确列出的**：`row cat` 返回的是该产品**所有可选**条件值，但提交时只写 inbox 优惠信息中**实际出现的**条件值。
  - ❌ 禁止：inbox 写了"地域：贵阳"，但提交时把 `row cat` 返回的全部 46 个地域都塞进去
  - ✅ 正确：inbox 写了"地域：贵阳"，只提交 `{"1": "gy"}`（仅贵阳）

### Step 3 · 组装优惠 JSON

按 Step 1 的拆解结果，把每个"优惠值 + 其条件取值集合"组装成一条 policy，**全部放进同一个 `policyList`**（格式见下方模板）。

> ✅ **此步（及 Step 4 提交）可用脚本代劳**——但脚本的**输入只能是 Step 1 的拆解表 + Step 2 的 code 映射**（都已人工核对），**绝不是** Excel 原始优惠文本。脚本只做"结构化表 → JSON"的机械拼装，不做任何文本解析。

**老商品库优惠 JSON 模板**

示例1：源数据"策略1 地域：广州，4折；策略2 地域：北京，5折；策略3 地域：上海，4.5折"
```json
{
  "21819_prepay": {
    "preference": {
      "preferenceType": "discount",
      "policyList": [
        {"conditions": {"1": "gz"}, "value": 0.4},
        {"conditions": {"1": "bj"}, "value": 0.5},
        {"conditions": {"1": "sh"}, "value": 0.45}
      ]
    }
  }
}
```

示例2：源数据"策略1 地域：广州、北京、上海，4折"（多地域同折扣，conditions 用数组）
```json
{
  "21819_prepay": {
    "preference": {
      "preferenceType": "discount",
      "policyList": [
        {"conditions": {"1": ["gz", "bj", "sh"]}, "value": 0.4}
      ]
    }
  }
}
```

示例3：源数据"策略1 地域：广州，一口价 0.00456元/GB/日"
```json
{
  "11243_postpay": {
    "preference": {
      "preferenceType": "fixed_price",
      "policyList": [
        {"conditions": {"1": "gz"}, "value": 0.00456}
      ]
    }
  }
}
```

示例4（**多维度条件 · 最易漏**）：源数据"策略1 地域：贵阳，指定价：1GE，6.5 折"
> 这行有**两个**条件维度——地域 + 指定价。`conditions` 必须是**两个 key**，缺一个都算配置错（compare 会报 `策略缺失 [地域=gy, 指定价=1]`）。两个维度的 attr_id 都要各自从该行 `row cat` 读（本例 10804：地域 `attr_id=1`、指定价 `attr_id=401`，`1GE→"1"`）。
```json
{
  "10804_postpay": {
    "preference": {
      "preferenceType": "discount",
      "policyList": [
        {"conditions": {"1": "gy", "401": "1"}, "value": 0.65}
      ]
    }
  }
}
```

示例5（**多维度 · 服务区域 + 带宽结算方式**）：源数据"策略1 服务区域：南美区，带宽结算方式：月95带宽，4.752 折"
> 同样两个维度都要进 `conditions`；两个维度的 attr_id 与取值 code 全部以该行 `row cat` 返回为准（本例 16155：服务区域 `attr_id=369`、带宽结算方式另有 attr_id）。
```json
{
  "16155_postpay": {
    "preference": {
      "preferenceType": "discount",
      "policyList": [
        {"conditions": {"369": "<南美区code>", "<带宽结算attr_id>": "<月95带宽code>"}, "value": 0.4752}
      ]
    }
  }
}
```

> 🚫 **多维度铁律**：源优惠文本里用逗号/顿号并列出现的**不同维度名**（地域 / 指定价 / 可用区 / 服务区域 / 规格 / 带宽结算方式 …）每一个都必须成为 `conditions` 里一个独立 key。**最常见漏配**：只解析了"地域"、把"指定价 / 带宽结算方式"整个维度丢掉 → 该 policy 的限定范围被放宽，compare 报 `策略缺失`。

| 字段                      | 说明                                                    |
| ------------------------- | ------------------------------------------------------- |
| `preferenceType`          | 优惠类型：`"discount"` 或 `"fixed_price"`               |
| `policyList`              | 策略列表，**源数据有几条策略就必须有几条 policy**        |
| `policyList[].conditions` | 优惠条件，key 为 attr_id（通过 `row cat` 获取）；**一条策略含几个维度就有几个 key**，value 格式见下方说明 |
| `policyList[].value`      | 优惠值，折扣类型时 0.4 表示 4 折；一口价类型时为金额（元） |

**conditions value 格式（必须区分）**：
- **单地域/单值**：value 为**字符串** → `{"1": "gz"}`
- **同条件多地域/多值**：value 为**数组** → `{"1": ["gz", "bj", "sh"]}`
- **不同地域不同折扣**：拆成多条 policy，每条 value 为字符串 → `[{"conditions":{"1":"gz"},"value":0.4}, {"conditions":{"1":"bj"},"value":0.5}]`

> ⚠️ **最常见错误**：源数据有 3 条策略（策略1/策略2/策略3 分别对应不同地域和折扣），只取第一条的折扣值。**必须逐条解析，全部写入 policyList。**

### Step 4 · 批量提交（全部 B 组行组装完后执行一次）

> Step 0–3 对每个 B 组行依次循环。全部行的 preference JSON 组装到**同一个 items 对象**中。

将所有 B 组行的 preference 数据合并为一个 JSON 对象，通过 `--compress` 一次性提交：

```python
import json, zlib, base64
items = {
  "1000638_postpay": {"preference": {"preferenceType": "discount", "policyList": [...]}},
  "11025_postpay": {"preference": {"preferenceType": "discount", "policyList": [...]}},
  # ... 所有 B 组行
}
compressed = base64.b64encode(zlib.compress(json.dumps(items).encode())).decode()

# 必须先写入文件再通过变量传入
with open('<CPQ_SESSION_DIR>/pref_b_compressed.txt', 'w') as f:
    f.write(compressed)
# 执行: COMPRESSED=$(cat <CPQ_SESSION_DIR>/pref_b_compressed.txt) && cpq row batch-update --compress "$COMPRESSED" --cpqcode {code}
```

> ⚠️ **禁止在命令行中直接用引号包裹 base64 值**（如 `--compress 'eJyt...'`）——base64 中的 `+`、`/`、`=` 等字符会被 shell 转义破坏，导致 `invalid stored block lengths` 错误。必须用文件或变量传入。

> ⚠️ **B 组 `row cat` 并发限制**：同时并行执行多个 `row cat` 时（如用 task 并行），可能导致 CLI 的本地 session cache 损坏（`cpqStore.json 解析失败`）。建议串行执行 `row cat`，或每批间隔 1-2 秒。

若返回部分行失败，根据失败原因修正对应行的 preference 数据后重新提交。

### Step 5 · 批量写后回查（不可省略 · 机器级硬校验）

用 `row list --fields preference` **完整**读回 B 组**每一行**的优惠信息（不是抽查一两行），逐行逐项核对。**无论用什么方法组装的 preference，宣布配置完成前都必须过这道校验**——出现下列任一情况即为配置失败，必须定位该行、修正后重提：

- ❌ `conditions` 里出现**非法 code**：任何一个条件值不在该行 `row cat` 返回的允许 code 集合里。典型信号——值里混入 `"4 折"` / `"3.5 折"` / `"10 折"` / `"X%"` / 中文地域名 / 顿号串 → 几乎一定是解析把折扣值或原文吞进了条件里。
- ❌ `conditions` 为空（条件型优惠的条件不得为 `[]` 或 `{}`）。
- ❌ **策略数不符**：`policyList` 条数 ≠ 源优惠文本里"不同优惠值 / 策略"的个数（典型：源 68 条被塌成 1 条）。
- ❌ **条件维度被丢**：源里出现的每个维度（地域 / 指定价 / 可用区 / 服务区域 / 带宽结算方式…）都必须在 `conditions` 里有对应 key；少一个维度即失败（典型：只写了地域、漏了指定价）。
- ❌ 某条 policy 的取值数量与优惠描述不一致（有遗漏 / 被覆盖 / 被多加）。

任一项不符 = 配置失败，修正后重提；**未做完整回查不得宣布配置完成**。

#### Step 5 机器自检门（必须执行 + 必须贴出结果）

回查不能只靠"人眼扫一遍"——**必须跑下面这段扫描，并把输出贴进回复**。它对 `row list --fields preference` 的读回文本做正则扫描，命中即为"脏 conditions"（覆盖已复现的所有事故：`"4 折"` 混入、中文名当 code、顿号串、`X%`）：

```python
import json, re, subprocess
# 完整读回 B 组各行 preference —— 必须用大 pageSize（-s）读全，默认只返回前 20 条会漏行
raw = subprocess.run(
    ["cpq", "row", "list", "-p", "1", "-s", "500", "--fields", "preference", "--cpqcode", CPQCODE, "--fmt", "json"],
    capture_output=True, text=True).stdout

# 逐个 conditions 值扫描非法信号：折 / % / 中文 / 顿号 / 空白 / 纯中文名
BAD = re.compile(r'[\u4e00-\u9fff]|折|%|、|\s')
violations = []
for m in re.finditer(r'"conditions"\s*:\s*(\{.*?\})', raw, re.S):
    try:
        conds = json.loads(m.group(1))
    except Exception:
        continue
    for attr_id, val in conds.items():
        vals = val if isinstance(val, list) else [val]
        for v in vals:
            if isinstance(v, str) and BAD.search(v):
                violations.append((attr_id, v))

if violations:
    print("❌ conditions 含非法值（脏 code），必须修正后重提：", violations[:50])
else:
    print("✅ conditions 值扫描通过（无折扣 token / 中文 / 顿号混入）")
```

- **命中任何一条 `violations` = 配置失败**，回到 Step 0 重查该行 `row cat`，用合法 code 重写后重提。
- 这段只是**机器兜底网**，拦得住"脏值"，但**拦不住**"策略数塌缩 / 维度漏写"（这两项没有源就无法机器判定）——所以上面 5 条人工核对**一条都不能省**。
- ✅ **正确姿势**：把这段扫描的输出、以及"每个 B 行 源策略数 N → 写入 policy 数 N"的逐行对照，一起贴进回复，才算通过 Step 5。

## 收尾 · 验证闭环（强制，不清零不算完成）

优惠配置**不是"提交完就结束"，而是"验证到零差异才结束"**。这是本流程质量的最后也是最硬的一道闸：

1. **保存 / 提交后必跑 Step 5 机器自检**（生产环境唯一门，不依赖任何基准单）——有 `violations` 就回 Step 0 修，修完重跑，直到通过。
2. **若本任务存在基准单**（如测试用例给了 `cpq compare <基准> <本单>`）：**必须**跑 compare，并让「优惠信息 / 折后含税 / 折后不含税」维度差异**清零**。
   - compare 报 `策略缺失 / 策略多出 / 策略数 N→M` → 说明某行维度漏了、code 错了或策略塌缩/多加，**逐行定位 → 回 Step 0 重查 row cat → 用拆解表重配 → 重提 → 再 compare**，循环到差异为 0。
   - **禁止**在优惠维度仍有差异时就宣布完成（历史上多次停在 80/95 分即收工，属违规）。
3. **修 bug 的正确方向**：差异几乎总是"解析/映射"环节的问题——回到 Step 0–2（row cat + 拆解表 + code 映射）修，**不要**在脏脚本上继续打补丁、更不要重新写正则去猜。

> 一句话闭环：**逐行 row cat → 人工拆解表 → 脚本组装 → 提交 → 自检/compare → 有差异就回 Step 0 → 直到零差异**。

## 常见错误形态对照

> 本表仅针对**第二步 B 组（带条件 / 多值行）**，A 组无条件单一值行不适用。全为结构示意，`<...>` 为占位符；真实字段 id / code / value 一律以该行 `row cat` 返回为准，不要照抄占位符。

| 失败模式          | ❌ 错误形态                                            | ✅ 正确形态                                                                       |
| ----------------- | ------------------------------------------------------ | --------------------------------------------------------------------------------- |
| 丢条件维度        | `conditions:[]`、`value:0.5`（明明限定了取值）          | `conditions:{"<字段id>":["<code1>","<code2>"]}`、`value:0.5`                       |
| 同维度差异抹平    | 所有取值塞进一条、统一 `value:0.8`（少数取值其实是 0.5） | 两条 policy：多数取值 `value:0.8` ＋ 少数取值 `value:0.5`                           |
| 原始文本当 code   | `value:["广州、上海、北京"]`（整串 / 中文名直接塞）    | 逐个映射展开 `value:["<广州code>","<上海code>","<北京code>"]`                     |
| 折扣值混入条件    | 正则切地域把折扣 token 也吞进来 → `conditions:{"1":["gz","sh","4 折"]}` | `conditions:{"1":["gz","sh"]}` + 折扣写在 `value`（`0.4`）；`"4 折"` 绝不进 conditions |
| 丢非地域维度      | 源"地域：gy，指定价：1" 只解析地域 → `conditions:{"1":"gy"}` | 每个维度都进 conditions → `conditions:{"1":"gy","<指定价id>":"1"}` |
| 跨产品套用 attr_id / code | 用全局字典或别的行的 id / code 填本行（例：本行地域应为 `{"2":...}`，却写成 `{"95":...}`） | 每行只用**该行自己** `row cat` 返回的 attr_id 与 code；二次修补时也先重查本行 |
| 循环写入覆盖      | 把同一行拆成多个 json / 分多次提交、每次只放一个取值   | 所有 policy 组装进该行同一个 json、一次批量提交                                   |
| 写后不查 / 空条件 | 写完即宣布完成；回查发现 `conditions:[]`               | `row list --fields preference` 批量回查：conditions 非空、code 合法、策略数对得上 |
