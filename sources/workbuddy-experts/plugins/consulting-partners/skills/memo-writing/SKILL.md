# 撰写：决策备忘录与研究报告

把分析结论变成能让决策者看完就能拍板的文字——不是信息的搬运工，是结论的压缩机。

## 核心方法

### 1. 决策备忘录

一页纸、约400字内，强制读者能在这一页上做出yes/no决定。四个不可妥协的标准：
- **极致简短**：每句话都要挣得它的位置
- **SCQA/RSC 故事线清晰**：情境→冲突→问题→答案；高管场景用 RSC 结论先行。读者永远不会问"所以呢"（见 references/storyline-scqa.md）
- **决策强制**：结尾是明确的决策请求（谁批、何时批），绝不是"进一步讨论"
- **证据密度**：每个论断都有数字或来源支撑，不靠形容词撑场面

**格式**：

```markdown
# {决策标题，≤10字，命名的是决定不是话题}

**现状**（3-4句）：决策前的世界是什么样，只讲事实和基线数字。
**矛盾**（2-3句）：发生了什么变化，或不决定会有什么风险，要有让人紧迫的数字。
**选项**（2-3个，各1-2句）：互斥选项，每个含最重要的取舍。不要在这里偷偷塞进推荐。
**推荐**：选定哪个选项，为什么在决策标准上胜出，引用最关键的证据。
**风险与缓解**（≤3条）：读者真正会问的三个风险，各配一句缓解方案。
**请求**（1句）：谁在何时前批准，谁负责下一步。
```

### 2. 金字塔原理结构化 + 行动标题 + 故事板

结论先行，向下用最多3条支撑论据展开，论据本身互斥穷尽（MECE），不需要读者按顺序读完才能get到重点。

**行动标题(灵魂,见 references/action-titles.md)**：每一节标题、每一页标题都必须是**完整的判断句**
(给结论)，不是"市场分析""问题总结"这类话题标签。避免"我们发现三个问题"式空洞总结——要说清
这些问题的共同性质或共同结果。

**标题故事板(做正式 deck/长报告前必做)**：先把每页只写一句行动标题，抽出所有标题连读，
**只读标题就能理解完整论证**才算故事线合格，再进入填充。SCQA/RSC/总分总/分CHAPTER 见 references/storyline-scqa.md。

### 3. 行业/市场研究报告

采用"框架生成→报告撰写"两阶段写法：
1. 先产出章节骨架（每章有分析目标、分析逻辑、核心假设、数据需求）
2. 数据到位后再写正文，每个子章节遵循"可视锚点（图表/表格）→数据对比→综合分析"的节奏
3. 每个子章节收尾要有一段至少200字的分析段，把数据背后的用户心理和战略含义讲清楚，不是简单复述数字

**格式**：

```markdown
# {研究主题}分析报告

## 摘要
[3-5条关键发现，执行摘要形式]

## 一、引言
[背景、研究目标、方法说明]

## 二～N、[各章节，按框架骨架展开]
### 2.1 [子章节标题]
[图表/对比表]
[数据对比]
[综合分析段，至少200字，遵循"数据→心理/行为→战略含义"链条]

## N+1、结论
[纯叙事，不用列表，客观综合，不重复给具体建议——建议已经在各章正文里]

## N+2、参考来源
[数据来源列表]
```

### 4. 六段输出合约

任何完整分析产出必须包含以下六个部分，缺一不可：

1. **结论（Bottom Line）**：一句话，明确方向或决定
2. **支撑论据（最多3条）**：各标注证据等级
3. **风险（至少2条）**：各配缓解方案
4. **反转条件（Kill Conditions，至少2条）**：什么数据点出现会推翻推荐
5. **下一步行动（至少2条）**：各有负责人、截止时间、验证指标
6. **未决问题**：还不知道什么，怎么去补足

漏掉风险、反转条件或下一步行动任何一项都是不完整的，不能以"这个case比较简单"为理由跳过。详细的六段合约说明和反模式清单见 `references/output-contract.md`。

## 工作流程

1. **确认写作目的**：读者是谁、这份文字要驱动什么决定、截止时间
2. **整合上游分析**：假设树结论、证据分析、测算结果，不重复分析，只做结构化压缩和叙事组织
3. **确定文体**：决策备忘录还是行业研究报告
4. **先定故事线 + 标题故事板**：SCQA/RSC 定叙事，写出全篇行动标题，通过"只读标题懂全文"测试后再写正文
5. **草拟正文**：备忘录按"标题→现状→矛盾→选项→推荐→风险→请求"顺序；报告按章节骨架逐章写
5. **执行六段合约自检**：逐项核对是否齐全
6. **删减30%**：初稿总是太长，删掉修饰词、模糊限定语（"可能"、"或许"）、不承担论证功能的过渡句
7. **留下成列的数字，不只是叙述里的单点数字**：只要这份稿子有可能转成 PPT
   （用户提了汇报/董事会/deck，或本来就是研究报告），每个核心论点后面都要把支撑数据
   **按可成图的形态**写下来——时间序列写全各期数值、对比写全各主体数值、构成写全各分项占比，
   而不是只在句子里带一个"同比增长 124.3%"。
   理由很实际：`deck-design` 的第一步是把这些数字清点成数据台账，台账凑不满页数就只能出文字卡片页。
   **散落在叙述里的孤立百分比画不出任何图**，成列的数字才画得出。
   删减 30% 时优先删形容词和过渡句，**不要删数字**。

## 交付闭环红线（每次输出前对照，任一不满足即不得收尾）

- **绝不零交付物收尾。** 收尾时面向用户的产物必须是成型的备忘录/报告，**不能**只有中间原料 JSON、只有一段"我需要先知道 XYZ"的反问、或只有"情况 A / 情况 B"的分叉选项。信息不全时也要交付"条件化结论 + Day-1 假设（已填具体数值并标 [E]/[A]）+ 待补数据清单"。
- **结尾必是可执行请求，不是开放式问题。** 严禁以"你想先深入哪个维度？""你先告诉我 A 还是 B"这类把决策踢回用户的句子结束；要信息只能作为已给结论之后的验证步骤附在下一步行动里。
- **每个关键数字在正文里真的带 [F]/[I]/[A]/[E] 标记**，不是心里分级；裸数字冒充事实即判不合格。

## 注意事项

- 备忘录里的"选项"部分绝不能藏着推荐，选项要真的中立列出取舍
- 禁止"进一步分析后续讨论"式的软收尾，最后一句必须是可以直接执行的请求
- 研究报告的结论章节不放具体建议，建议应该已经分布在各正文章节
- 数字千分位统一用英文逗号，专业术语保留业界通用英文缩写（TAM、CAC、IRR等）不强行翻译
