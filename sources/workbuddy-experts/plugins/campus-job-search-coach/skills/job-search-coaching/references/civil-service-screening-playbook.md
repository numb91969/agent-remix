# 考公岗位筛选与报考决策

## 一、定位与边界

本流程服务准备国考、省考、选调生和事业单位岗位的在校生与应届生，回答"职位表里哪些岗位能报、哪些值得报、怎么收敛到报考目标"。

| 纳入 | 不纳入 |
|---|---|
| 岗位筛选方法论、硬门槛批量筛选 | 行测/申论等笔试备考辅导（不承接，引导用户使用备考类服务） |
| 报考决策（国考/省考/选调/事业编对比） | 职位数据库实时代理与岗位状态保证 |
| 结构化面试训练的结构与表达 | 录用概率预测、分数线预测 |
| 政审、体检、服务期等环节说明 | 薪资待遇具体数字 |
| 冲/稳/保分档（依据用户提供的历年数据） | 历年分数线的口头报价（只引用用户提供或可核验来源的数据并标注年份） |

## 二、输入状态

| 状态 | 已有材料 | 默认动作 |
|---|---|---|
| 完整 | 职位表文件 + 个人条件 | 走第四节全流程，输出五张表和报考建议 |
| 可用 | 只有职位表 | 先解析表头并做字段映射，只问一轮个人条件（学历、专业、政治面貌、基层年限、应届身份） |
| 可用 | 只有公告链接或岗位名称 | 按来源规则核验公告原文；核验失败请用户提供官方材料，不凭记忆补写 |
| 阻塞 | 只有模糊意向 | 给筛选模板与官方入口（assets/civil-service/official-portals.json），只问一个最关键问题（报考类型或专业） |
| 风险 | 涉及政策边界争议、疑似诈骗 | 按第八节话术与安全边界处理 |

## 三、三条链路

```
首选：用户上传职位表（官方 Excel）
  → 模型做表头映射 → 规则引擎筛选 → 输出候选清单
次选：检索核验单个政策条款
  → 按 source-notes.md 核验流程，标注来源 + 访问日期
兜底：无法核验时明说
  → 不猜、不用二手来源补位，给官方入口清单
```

每年变动的数据（笔试合格线、职位级进面分、报录比、报名人数）一律不内置判断，只引用用户提供或可核验来源的数据，并标注来源与年份。

## 四、技术架构：模型映射 + 规则引擎

```
用户上传职位表（任意来源格式）
  ↓
① 模型读表头（数十列，量小）→ 生成字段映射：
   哪列是专业/学历/学位/政治面貌/基层经历/应届/户籍/备注
   → 映射结果先展示给用户确认，再进引擎
  ↓
② 归一化 → 标准字段（degree/major/political/grassroots/
   fresh_requirement/household/other_requirements）
  ↓
③ scripts/position_screen.py 规则引擎筛选（硬门槛）
  ↓
④ assets/civil-service/ 数据对照
   major-catalog.json（专业门类-大类对照）
   official-portals.json（官方入口与数据获取路径）
```

分工原则：

| 环节 | 谁做 | 原因 |
|---|---|---|
| 表头识别/字段映射 | 模型现场做 | 格式五花八门，模型适应性最强；映射错了用户能发现 |
| 业务规则（学历层级、应届判断、专业大类匹配） | 规则引擎固化 | 规则错了用户无从察觉（漏筛），必须确定性执行 |
| 专业目录大类对照 | 数据文件 | 模型记忆可能记错大类归属；对照不上时转用户确认，不猜 |
| 备注、加试、体检等特殊要求 | 人工确认 | 透传原文，不自动判断 |

引擎调用方式：把映射后的职位与个人条件整理为 UTF-8 JSON，运行：

```bash
python3 scripts/position_screen.py /path/to/input.json -o /path/to/output.json
```

引擎输出 pass / fail / needs_review 三态：fail 为确定不符合；needs_review 保留待人工确认，不淘汰。筛选顺序建议：专业 → 学历/学位 → 政治面貌 → 应届限制 → 基层经历 → 户籍。

## 五、筛选方法论

### 1. 五张表

按以下顺序产出，缺用户信息的项保留占位并标注待确认：

1. **个人硬条件卡**：身份（应届/择业期内/往届）、学历学位、专业名称（对照专业目录）、政治面貌、基层年限、年龄、户籍/生源地、资格证书、特殊身份（退役军人/三支一扶等）、模考成绩（行测+申论总分，用于冲稳保）
2. **岗位筛选总表**：引擎输出的 pass + needs_review 岗位，含序号、招录机关、用人司局、职位名称、职位代码、工作地点、层级、各门槛、招录人数、备注
3. **竞争与风险信息**：用户提供或核验获得的历年进面线、报名人数、竞争比、服务期限制；每条标注来源与年份
4. **偏好评分表**：地区匹配度 25%、岗位内容与专业相关度 20%、部门层级与发展 15%、待遇（定性）15%、上岸难度 15%、工作强度 10%；加权总分只用于排序，不等于录取概率
5. **意向岗位决策卡**：报考理由（≤3 条）、主要风险、待确认问题（报名前电话确认）、时间节点（公告→报名→资格审查→缴费→笔试→面试，以当年公告为准）

### 2. 考公特有策略

通用投递组合策略（保底/匹配/冲刺、用足筛选价值、避低门槛陷阱、HC 容错、JD 末尾必读）见 `application-decision-playbook.md` 投递组合策略章节。此处只写考公实例差异：

- **避开三不限**：不限专业/学历/户籍的岗位竞争比通常最高，手握应届或定向身份的用户尤其不要浪费筹码
- **定向岗位优先**：有三支一扶、西部计划、大学生村官等经历的用户优先选定向招录岗
- **招录人数容错**：1:3 进面比例下，招 3 人的岗位有 9 个进面名额，容错远大于招 1 人
- **备注栏必看**：性别、服务期、经常出差、加试、体检特殊标准是最常见踩坑点，引擎已透传备注，必须逐条与用户确认
- **报名动态决策**：不第一天报也不最后一天报；先观察 2—3 天，截止前 2 天看官方公布的实时报名人数，在备选中选增长慢的（实时数据以官方报名系统为准）
- **目标分层**：求快上岸侧重基层定向岗、紧缺专业岗；求长期发展侧重省会及以上城市、专业技术岗

### 3. 冲/稳/保分档

用户提供模考成绩（行测+申论总分）与目标岗位历年进面分（用户提供或标注来源的核验数据）时，按成绩与历年线差距分档输出：

- 冲：成绩低于历年线 5 分以内
- 稳：成绩在历年线上 5—15 分
- 保：成绩高于历年线 15 分以上

分档必须附"历年数据不代表今年"提示。无历年数据时明确说明无法分档，不用估算补位。

## 六、报考决策框架

对比国考、省考、选调生、事业编时，按以下维度整理，事实层信息（考试时间、招录规模）以当年公告为准：

| 维度 | 说明 |
|---|---|
| 报考条件 | 应届限定、党员、学生干部、专业范围、学历层次 |
| 考试科目与时间 | 与用户备考周期匹配度 |
| 发展路径 | 单位层级、职级序列、调动空间 |
| 竞争强度 | 基于用户可提供的历年数据，无数据时明说 |
| 机会组合 | 是否可同时报考多种考试（以各公告规定为准） |

## 七、面试差异训练

结构化面试（答题结构、时间控制、观点组织）、无领导小组讨论（角色选择、进程推进）、材料题（信息提取与归纳）与 HR 行为面试的差异只在**形式与结构**。训练时：一次一题、只改结构与表达、不代替评分标准判断内容正确性。通用面试训练机制见 `interview-playbook.md`。

## 八、高风险问题应答规范

| 问题类型 | 示例 | 处置 |
|---|---|---|
| 边界模糊政策（裁量权在招录机关） | "我算应届生吗""这段实习算基层经历吗""我的专业符合 XX 类吗" | 转确认：引官方原文 → 说明存在裁量空间 → 指引电话确认 |
| 可核验政策事实 | "2027 国考报名时间""报考条件是什么" | 核验回答：官方原文 + 来源名称 + 访问日期 |
| 无官方来源数据 | "这个职位去年进面线""待遇怎么样" | 进面分只引用用户提供或标注来源年份的数据；待遇不给数字 |
| 录用判断 | "我报这个岗位希望大吗""分数线大概多少" | 拒绝预测：只做证据覆盖与冲稳保分档 |

统一话术：

- 转确认类：根据 [公告名称] 第 X 条原文：「……」。这一条在 [用户具体情形] 上存在解释空间，最终认定权在招录机关。建议直接拨打职位表中该岗位的咨询电话确认，确认后再报名。
- 核验回答类：根据 [来源名称]，[访问日期] 核验：……。以当年官方公告为准。
- 数据引用类：该岗位 [年份] 进面分为 XX 分（数据来源：[来源]，仅供分档参考，不代表今年）。
- 拒绝预测类：我不做录用概率或分数线预测。可以帮你做的是：列出该岗位的硬门槛符合情况、冲稳保分档、以及和其他候选岗位的对比。

原则：低风险区放开做，高风险区做"指引者"不做"裁判"。

## 十、禁止项

- 不承接行测、申论等笔试备考辅导；请求出现时明确说明边界并引导备考类服务。
- 不预测录用概率、分数线、竞争比走势。
- 不编造职位数据、分数线、报名人数；无来源的数据一律不写。
- 不把第三方机构（中公/华图/粉笔等）数据写成事实，必须标注二手来源与年份。
- 不提供薪资待遇具体数字。
- 不基于性别、民族、户籍等敏感属性给出报考或不报的建议。
- 不凭记忆输出当年政策细节（报名时间、报考条件），必须走核验链路。
- 专业大类对照不确定时转用户确认，不猜测归属。
