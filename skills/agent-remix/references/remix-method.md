# 多专家 Remix 方法

## 选择来源

先按目标职责拆成能力簇，再为每个能力簇选来源。例如企业 CFO 可拆成经营分析、预算与现金流、财务内控、税务合规、融资与资本配置、经营沟通；行政+HR 可拆成招聘、绩效与晋升、员工关系、薪酬福利、制度流程、行政运营。每个能力簇至少保留一个直接来源，关键流程最好有第二个来源交叉验证。

推荐的证据表：

| 能力簇 | 主来源 | 辅来源 | 保留内容 | 不带入内容 |
| --- | --- | --- | --- | --- |
| 角色身份 | 职位最匹配 agent | 文化/行业 agent | 称谓、使命、边界 | 另一个 agent 的名字 |
| 方法论 | 专业流程 agent | 审核/分析 agent | 步骤、检查清单、指标 | 内部编排命令 |
| 输出格式 | 交付型 agent | 沟通型 agent | 表格、结论、行动项 | 与平台绑定的 UI 指令 |
| 风险控制 | 合规/审计 agent | 行业合规 agent | 红线、审批点、证据要求 | 未验证的法律结论 |
| 技能 | 能力簇对应 skill | 通用文件/表格 skill | 触发条件、输入输出 | 私有凭据与绝对路径 |

## 融合而不是拼接

不要把多个完整系统 prompt 依次串起来。先做去重：身份只保留一份，职责合并成能力树，方法按任务阶段排序，重复的语气和欢迎语删除。对冲突指令使用以下优先级：用户当前要求 > 企业安全/合规边界 > 目标职位职责 > 可验证的专业方法 > 来源 agent 的风格偏好。

对 source prompt 的首段进行单独处理：若其中有“只能自称某专家名、不能说 AI/Agent/模型”的约束，只有在用户要求保留该身份时才放到最终 prompt 的最开头；把来源名替换成目标 agent 名称，避免成品误称为源专家。其他角色定义和能力清单可作为候选内容，但必须检查是否含平台专属命令。

## 技能依赖决策

| 情况 | 决策 | 处理 |
| --- | --- | --- |
| 纯 Markdown/表格/本地文本 | direct | 复制技能正文，并保留触发条件 |
| 需要和专家包保持本地关联 | symlink-audit | 本地用相对软链或 `links.json`；Git 导出 materialize 文本或保存 link map |
| 需要 `.NET`/私有 MCP/内网/付费库 | exclude | 只记录能力、前置条件和降级方案 |
| 需要账号、token、master key | exclude | 不复制凭据，不在 prompt 中硬编码 |
| 需要特定二进制或大数据集 | exclude 或 manifest-only | 记录文件名、大小、hash、获取方式 |

软链是索引和可审计关系，不是把用户机器路径伪装成可移植安装包。发布平台若不支持软链，优先带入经过审计的 `SKILL.md` 文本或在技能清单中声明“未绑定”。

## 成品验收

在发布前至少做四个检查：

1. 身份检查：名称、首段自称、称谓和公司职责一致；
2. 能力检查：每个核心能力簇有来源和可执行输出；
3. 依赖检查：技能全部标记 direct/symlink-audit/exclude，外部依赖可见；
4. 安全检查：没有 API key、cookie、master key、绝对用户路径、虚假的“已执行”声明。

报告要能回答“用了哪些 agent、各自贡献了什么、为什么排除某些内容、绑定了哪些 skill、发布是否成功”。
